# Run discipline

A run is a directory of files that makes consequential work reconstructable months later. It is a
convention backed by a human, not a workflow engine. Nothing here blocks a turn.

## 1. Call the tier first

| Tier | The work | What it owes |
|---|---|---|
| `read` | Observing; re-adjudicating a prior finding; answering a question about a system | A criterion, evidence, and verdicts |
| `change` | Modifying a system, config, deployment, or data | Everything `read` owes, plus base and result state, a **tested** rollback, and an independent review **before** the change is approved |

Two failure modes, both ceremony, in opposite directions: a `change` run with no independent review,
and a `read` run that convenes a reviewer when no prior finding is being retired. The second one
actually happened here.

## 2. The default answer is "no run"

Say so and stop. No run for small reads, single-command claims, ordinary code edits, or work with no
prior finding to retire. The cost is real: the one executed run spent ~20 minutes of subagent compute
and ~8.1M tokens for two claims, and its own retrospective called that "borderline."

If the work is consequential, continue.

## 3. Write the criterion before you probe

```
runs/<YYYY-MM-DD>-<slug>/
├── TASK.md           authored at intake — request, criterion, tier, gates, state
├── EVIDENCE/         one file per command: the exact command and its exact output
├── LEDGER.md         one row per claim: claim · grade · source · status · contradicts · superseded_by
├── REVIEW.md         independent verdict from EVIDENCE/ alone, including dissent
├── RECEIPT.md        generated by a tool — never hand-edited
└── RETROSPECTIVE.md  what the procedure cost, and whether it helped
```

Never open the directory before a criterion exists. Read
[references/task-frontmatter.md](references/task-frontmatter.md) for the field contract when
authoring `TASK.md`.

## 4. The whole discipline, compressed

Five lines:

1. Before starting, name the one command that would prove you failed.
2. Run it before and after. Keep the raw output of both.
3. If it fails and you proceed anyway, record that you proceeded, and why.
4. If you cannot determine something, write `UNKNOWN`. Never write a plausible answer.
5. Keep the file. The summary is what you will forget; the command is what you can re-run.

- [ ] **Before:** one line — *"Done when `<command>` prints `<expected>`."*
- [ ] **Before:** run it, save the raw output.
- [ ] **During:** if you deviate from the criterion, write the deviation and the reason.
- [ ] **During:** anything undecidable goes down as `UNKNOWN`, never as a guess.
- [ ] **After:** run the check again, save the output, compare.
- [ ] **After:** if you changed the machine, write down how to undo it — and whether you tested that.

## 5. Phase order, and what each phase leaves behind

| Phase | Leaves behind | Owner |
|---|---|---|
| INTAKE | `TASK.md` with a falsifiable criterion | Human |
| UNDERSTAND | The relevant system read; assumptions written as questions | Collector |
| PLAN | Approach, alternatives, blast radius, rollback | Human — no agent holds this today |
| RESEARCH | Claims graded; primary sources over summaries | Collector, evidence |
| IMPLEMENT | The change — **only after approval** for gated categories | Human-driven |
| VERIFY | Every claim has a verdict and an evidence file | Evidence |
| REVIEW | An independent verdict from `EVIDENCE/` alone; dissent recorded | Reviewer |
| HUMAN DECISION | Confirmed, corrected, or overridden — **and recorded** | Human |
| DELIVER | Reversible; state recorded; artifacts listed | Human |
| TEACH | What happened, why, what to reuse, what not to | Author |

## 6. Delegation

Match the role to the job, and remember that a named agent's deliverable is a **file**, not a chat
message — the transcript keeps only the agent's final message, so an unclaimed file is a lost
finding.

- One context **collects** facts and writes them to `EVIDENCE/`.
- A different context **adjudicates** claims to verdicts — see `evidence-check`.
- A third, independent context **reviews** from the evidence alone — see `acceptance-review`.

Never let the context that gathered the facts be the one that judges them. Arguments about the
*number* of agents are unproductive; the separation is the point.

## 7. What is not enforced

Exactly one phase has a mechanical enforcement path (IMPLEMENT, via a pre-tool gate) and it is
unbuilt. Nothing blocks a turn. A missing verdict is **reported**, never enforced. Boundaries are the
harness's permission ladder plus the human; a `deny` rule on a path is deterrence, not a sandbox,
because shell arguments are not path-gated. Write this honestly rather than implying a guarantee that
does not exist.

## Known limitations

- The session transcript lives outside the run directory. Record its path in `TASK.md` at intake, or
  the record cannot prove its own process claims.
- Agent internals are not captured — only the final message and whatever files it wrote.
- Whether a skill was activated is not observable from any transcript. Record intent, and print the
  literal `UNKNOWN — not observable` for activation. Never infer it.
